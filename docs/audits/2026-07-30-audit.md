## Findings

### 1. The "Live" connection indicator is hardcoded and can never report a failure · `P1`

**Evidence:** `src/lib/websocket/hooks.ts:15-21` is the only writer of connection status in the codebase:

```ts
export function useWebSocket() {
  const { setConnectionStatus } = useStreamStore()

  useEffect(() => {
    setConnectionStatus('connected')
  }, [setConnectionStatus])
}
```

`grep -rn "setConnectionStatus" src/` returns exactly four hits — the store's type (`store/useStreamStore.ts:16`),
its setter (`:30`), and the two lines above. There is no other caller, and no error or failure path.

The value is rendered in two always-visible chrome surfaces:
- `src/components/layout/StatusBar.tsx:51` — `Data: {connectionStatus === 'connected' ? 'LIVE (polling)' : …}`, coloured `text-emerald-400` (`:25`)
- `src/components/layout/Sidebar.tsx:461-464` — a green status dot plus the label `Live` (`STATUS_LABELS`, `Sidebar.tsx:161-166`)

`useWebSocket()` is invoked unconditionally on every dashboard render (`src/app/(dashboard)/layout.tsx:17`).

**What is wrong:** The hook's own comment explains it is a "status shim" left behind after the M8
sweep removed the real socket client. The shim kept the *green* branch and dropped every other one.
`'connecting'`, `'disconnected'` and `'error'` are unreachable — dead branches in both components.

**Why it matters:** The app tells the user "Data: LIVE (polling)" in green while a `/live-data/*`
route is 503ing, rate-limited, or serving FALLBACK. That is a fabricated live signal on the exact
chrome a user checks *before* trusting a price — the same class of defect that de-routed
`/global-adoption` under T5, and it contradicts the README's stated data-honesty principle.
(Distinct from the `StatusBar.tsx:41` hardcoded market-`OPEN` literal already recorded in
`PRELIMINARY-FINDINGS-2026-07-30.md`; that is a different line and a different signal, though the
same class. Both sit in the same status bar, so a user sees two independent fabrications side by side.)

**Suggested fix:** Either drive the status from something real that already exists — React Query's
global fetching/error state is the obvious seam — or delete the indicator and its three unreachable
branches. A shim that only ever reports success is worse than no indicator.

*Importance:* High — always on screen, and it is the signal that gates trust in every number below it. · *Efficiency:* High — one hook, ~6 lines, plus removing dead branches. · *Practicality:* High — no data dependency; the React Query state is already in the tree.

### 2. The documented procedure for re-enabling the auth wall does not re-enable it · `P2`

**Evidence:** `src/app/(dashboard)/layout.tsx:19-23`:

```ts
// LOGIN TEMPORARILY DISABLED (by request, until the risk framework is done).
// The auth wall is fully off so it cannot affect the build or block access.
// To RE-ENABLE later: restore `import { LIVE_DATA } from '@/lib/constants'`
// and `const REQUIRE_AUTH = !LIVE_DATA`, and revert the /login redirect.
const REQUIRE_AUTH = false
```

`src/lib/constants.ts:14`:

```ts
export const LIVE_DATA = true
```

So the documented restoration, `const REQUIRE_AUTH = !LIVE_DATA`, evaluates to `false`. Following
the instruction exactly leaves the wall off. `LIVE_DATA` is not a toggle — `CLAUDE.md` states it is
hardcoded `true` with no env override, and `lib/websocket/hooks.ts:8` says the same in its own comment.

Two further contradictions in the same pair of files:
- `src/app/(auth)/login/page.tsx:16-19` gives a **different** recipe for the same task — "set this to false and set `REQUIRE_AUTH = true`" — which is the correct one. Two recipes, one broken.
- Both comments gate on "until the risk framework is done." That condition is met: `docs/architecture/risk-scale-spec.md` exists (47,661 bytes), `docs/TASK-QUEUE.md:36-42` records R1 as complete, and `README.md:57` states the Safety Score has been "🟢 **Live** since 2026-07-18." Nobody revisited the flag.

**What is wrong:** A safety control is off, its stated expiry condition has since been satisfied, and
the primary note on how to switch it back on is wrong.

**Why it matters:** Whoever re-enables auth — likely under time pressure, before a first
deployment — follows `layout.tsx` because that is where `REQUIRE_AUTH` lives, sees no change in
behaviour, and may conclude the wall is on when it is not. The blast radius is bounded today only
by `isLocalUserModeAllowed()` (`src/lib/auth/session.ts:44-48`), which denies local-user mode in
production by default; that default is the only thing standing between a public deploy and every
anonymous visitor sharing one account, as the comment at `session.ts:24-27` itself warns.

**Suggested fix:** Delete the `!LIVE_DATA` recipe, keep the single correct one in
`login/page.tsx`, and either act on the now-satisfied condition or replace it with a condition that
has not already passed.

*Importance:* Medium — no user-visible wrong number, but it is a security control with misleading operating instructions. · *Efficiency:* High — a comment correction plus one decision. · *Practicality:* High — the correct recipe is already written in the sibling file.
