**New work the H3 run surfaced**, tracked in DATA-AVAILABILITY.md's action
items rather than as audit findings, since they postdate this report: the
news outage (`news` and `v1 news` both failing), live staking coverage at
4 of 51, and a macro re-run now that the harness covers it.

**M3 as executed, part two — pinning (the undici decision, reversed).** The
first pass stopped at resolve-time validation and recorded the residual
rebinding window as accepted, on the grounds that closing it meant adding
undici right after M8 removed six packages. That call was put to the owner and
overturned: `undici` is now a dependency, and `lib/server/pinnedFetch.ts`
connects to an address `resolvePublicAddresses()` approved instead of handing
the hostname to the socket. TLS is untouched — undici sends `servername` from
the URL, so SNI and certificate validation still use the name.

One implementation note worth keeping: it uses **undici's own `fetch`**, not
the global one. A dispatcher only works with the fetch it was built for, and
Node's built-in fetch is backed by a vendored undici whose major version tracks
the Node release — mixing them fails with `InvalidArgumentError: invalid
onRequestStart method`, which is exactly what happened on the first attempt.
Importing both from the same package also means a Node upgrade can't silently
disable the pin.

The cost, stated because it is a real regression: requests carrying a custom
dispatcher are **not covered by Next's fetch cache**, so `next: { revalidate }`
is inert on the pinned paths and custom feeds now hit upstream once per
request. Built-in providers are untouched — the videos route branches on
whether the URL came from user input precisely so YouTube feeds keep their
600 s revalidate. Custom feeds are opt-in and few; that is the price of not
being rebindable.

**M3 as executed, part one — resolve-time validation.** `urlSafety.ts` now has
two layers: the original synchronous string check, and
`validatePublicHttpUrlResolved()`, which resolves the hostname and rejects if
**any** returned address is private — not just the first, since which address
the socket picks is not ours to choose. Every fetch-time call site was moved to
it (custom feeds incl. each redirect hop, news, quotes, videos, video-analyze,
the Integrations test-fetch). The two save-time checks in `config/route.ts`
stay string-level on purpose: a provider config should not be rejected because
DNS happened to be down when the user clicked Save.

This closes the entire no-DNS-control-needed class — a plain
`A 169.254.169.254`, a CNAME into an internal zone, a split-horizon name. True
rebinding needed the transport change described above.

One pre-existing bug surfaced while testing: the dotless-hostname heuristic
(`!host.includes('.')`) rejected **every** IPv6 literal, public ones included,
since `URL.hostname` returns them bracketed. That was an accident of the
heuristic, not a decision — `isPrivateIpv6` exists precisely to sort v6 into
public and private. Address literals are now exempted from the heuristic and
judged on the address.

**M8 as executed.** The finding's inventory was verified file-by-file before
anything was deleted, and two of its claims needed correcting: `lib/api/
client.ts` was *not* importer-free (four api modules imported it), and
`lib/websocket/client.ts` was reachable by type import from `useStreamStore`.
Both were still dead in the sense that matters — every call site sat behind an
`if (LIVE_DATA)` early return and `LIVE_DATA` is a hardcoded `true` — so the
fix was to strip the unreachable branches, not just unlink the files. That
cascade orphaned a second tier the finding didn't list (7 hooks, 8 api methods,
6 types, 4 constants), removed here too; leaving it would have re-created the
finding on the next audit. `RiskHeatmap`, `LiveAlertRow`, and the `useWebSocket`
status shim were kept — all three have live consumers.

## Findings, ranked

### 🔴 CRITICAL

**C1 — Production build is broken.** `next build` fails route-type validation: `src/app/live-data/macro-news/route.ts:176` exports `classifyPillar`, which Next.js forbids from a route file. The export exists so `src/lib/server/__tests__/macroPillar.test.ts:2` can import the classifier — so vitest passes, `tsc --noEmit` passes, and dev mode works, which is exactly why this survived: only a production build catches it. **Remedy** (small, behavior-neutral): move `classifyPillar` (and its types) to `src/lib/server/macroPillar.ts`; import it from the route and the test. Until then no production deploy is possible, and the CI Docker build job should also be failing on this.

### 🟠 HIGH

**H1 — SSRF: custom-feed data fetches follow redirects into private address space.** `src/lib/server/customFeeds.ts` → `fetchCustomUrl()` validates only the *initial* URL via `validatePublicHttpUrl`, then calls `fetch(finalUrl, …)` with no `redirect` option (default: follow). A user-added feed URL that passes validation but 3xx-redirects to `http://169.254.169.254/…` or an internal host is followed and its body parsed/returned. The config *test* path already does this right (`src/app/live-data/config/route.ts:186` uses `redirect: 'manual'` with a comment explaining why) — the production data path skipped the same defense. Remedy: `redirect: 'manual'` (or re-validate every hop) in `fetchCustomUrl`.

**H2 — Stablecoin issuer/attestation snapshot is ~20 months old and feeds the live risk engine.** `src/lib/data/stablecoinMeta.ts:10` — `META_AS_OF = '2024-12-01'` (603 days); individual `lastAttestedDate` values reach back to 2024-09-30 (~20 monthly attestation cycles behind). Consumed by `live-data/risk-scores/route.ts:187`, `live-data/reserves/route.ts:112`, and `lib/risk/profiles/stablecoin.ts` — i.e. it shapes published Safety Scores, not just display copy. The date *is* disclosed in small print on Reserves and the Coin Registry, but unlike `transferFees.ts` there is **no age computation, no staleness threshold, no banner escalation**. Remedy: refresh the snapshot, and give it the transferFees-style provenance machinery so it can never silently age like this again.

**H3 — The documentation layer has re-created the exact "stale memo" failure mode this repo already documented.** Three docs would actively misdirect an agent or contributor today:
- `docs/ROADMAP.md:347-349` (owner backlog, 2026-07-26) instructs "decide the single risk scale before more profiles land," citing `docs/MARKET-ASSESSMENT.md` — but R1/R2 settled and shipped that decision on 2026-07-19 (canonical 0–100 higher-is-safer, `riskCanonical`, Safety Score rename — all verified in code). MARKET-ASSESSMENT also still claims risk scores "show N/A," false since 2026-07-18.
- `DATA-AVAILABILITY.md` — the doc CLAUDE.md calls "the authoritative record, consult it when in doubt" — still says only 4 of 28 staking rates are live (`:75`), invalidated by the 2026-07-24 staking-rates rewrite (PR #37, DefiLlama Yields + ~10 native-rate sources), and has **no rows at all for the Macro module** (`macro-news`, `fx-rates`, `fx-rates-extended`, `treasury-yield-curve`, all shipped 2026-07-21 after its last regeneration). It claims "all 51 route files comply"; disk has 57. It also still describes Stooq as a quote-ladder rung (removed).
- `README.md` (last rewritten 2026-07-15): "four configurable agents" (there are 11), "composite risk scoring in development, shows N/A" (live since 07-18), no Macro module, 43 staking providers (55).
- The canonical risk-scale spec itself (`docs/architecture/risk-scale-spec.md`, referenced by TASK-QUEUE and both R2 assessments as the source of truth) **is not on main** — the branch `docs/risk-scale-spec` isn't in this clone. Future risk work is pointed at an unreachable document.

Remedy: regenerate DATA-AVAILABILITY.md (`npm run data-sources` + harness run on the owner's machine), strike or annotate the settled items in ROADMAP/MARKET-ASSESSMENT, refresh README's counts, merge the risk-scale spec to main. Notably, `DATA-SOURCES.md` is genuinely generated and current — it's the model the others should follow.

### 🟡 MEDIUM

**M1 — Crypto module is `optional: true` but none of its 11 pages are gated.** `src/lib/modules/registry.ts:86-104` declares crypto optional with 11 route prefixes, yet zero of those pages carry `<ModuleGate>` — disabling the module hides the sidebar section while every route remains reachable by URL. Every *other* optional module is gated one-per-page (equities ×8, macro ×8, funds ×4, builder ×1 — verified complete). Cosmetic today (entitlements are client-side), but the asymmetry silently carries over the day the gate becomes a server-side entitlement check.

**M2 — Dual auth stacks; one of them is dead and a comment lies about which.** The `/login` page posts through `useAuthStore.ts:44` → `authApi.login` → axios → the legacy Python backend (`:8000/auth/login`). Meanwhile a fully wired Auth.js stack (nextauth route, signup with bcrypt cost 12, `session.ts`) sits beside it, unconnected — and `src/app/api/auth/[...nextauth]/route.ts:3` claims "sign-in posts here from the /login page," which is false. This needs an owner decision: if Auth.js is the future, the login page should post to it and the axios/`client.ts`/`auth.ts` cluster (~250 LOC + the axios dep) becomes deletable; if the legacy backend is the future, the comment and the signup route are the dead half. Related: with `LIVE_DATA` hardcoded true, this login flow is the **only** runtime path into the entire 11.7k-LOC `backend/` directory — the docs' "auth/agent features" claim overstates it, since agents now run first-party.

**M3 — SSRF hardening is string-level only (DNS rebinding gap).** `src/lib/server/urlSafety.ts:36-60` blocks private/reserved ranges by hostname literal but never resolves-and-pins, so a hostname whose DNS answer is (or becomes) a private IP passes. Thorough otherwise (IPv6-mapped, CGNAT, link-local, embedded credentials). Standalone this needs attacker-controlled DNS; combined with H1 it's the classic bypass pair. Fix H1 first; consider resolve-time enforcement after.
